  1. 题目

  在 Docker 环境下构建多智能体（Multi-Agent）协作的推理调度系统，通过用户接口 Agent、推理策略 Agent、一致性校验 Agent 三个智能体的协同，实现对 FP16/INT4
  双精度推理引擎的自动调度、显存监控与一致性校验，验证多智能体协同在高并发场景下的推理吞吐量提升。

  ---

  2. 算法阐述或实验步骤说明

  2.1 算法原理

  (1) 多智能体协作架构

  多智能体系统将复杂任务分解为多个自治 Agent，各 Agent 独立运行、通过消息通信协同完成整体目标。本实验构建三个核心 Agent：

  用户请求 → 用户接口Agent(gateway) → 任务队列(Redis) → 推理策略Agent(strategy)
                                                            │ 选择FP16/INT4
                                      ┌─────────────────────┴──────────┐
                                      ▼                                ▼
                               vllm-fp16(GPU0)                 vllm-int4(GPU0)
                                      └─────────────────────┬──────────┘
                                                            ▼
                                     一致性校验Agent(validator) ──▶ 返回结果

          显存监控Agent(monitor) ──▶ 每2s采集nvidia-smi ──▶ Redis ──▶ strategy负载决策

  三个 Agent 职责：

  ┌───────────────────────────────┬────────────────────────────────────┐
  │             Agent             │                职责                │
  ├───────────────────────────────┼────────────────────────────────────┤
  │ 用户接口 Agent（gateway）     │ 接收请求、投递任务、SSE 返回结果   │
  ├───────────────────────────────┼────────────────────────────────────┤
  │ 推理策略 Agent（strategy）    │ 规则控制器选择 FP16/INT4 精度      │
  ├───────────────────────────────┼────────────────────────────────────┤
  │ 一致性校验 Agent（validator） │ 用另一精度模型交叉复核，标记一致性 │
  └───────────────────────────────┴────────────────────────────────────┘

  (2) 通信框架：Redis 消息队列

  Agent 间通过 Redis 消息队列异步通信，实现解耦的任务传递：

  gateway ──LPUSH tasks:pending──▶ Redis ──BRPOP──▶ strategy
                                                      │ 选择FP16/INT4
                                                      ▼
                                        Redis tasks:validating ──BRPOP──▶ validator
                                                                            │ 交叉复核
                                                                            ▼
                                          Redis tasks:{id}:result ──PUBLISH──▶ gateway

  核心队列：
  - tasks:pending：待调度任务队列（LPUSH/BRPOP）
  - tasks:validating：待校验结果队列
  - tasks:{id}:result：结果发布通道（PUBLISH/SUBSCRIBE）
  - gpu:usage：显存监控数据（monitor 写入，strategy 读取）

  (3) FP16 与 INT4 量化

  FP16（半精度浮点）：模型权重以 16 位浮点数存储，精度高、推理慢、显存占用大。

  INT4（4 位整数量化）：通过 GPTQ 量化将权重压缩为 4 位整数，显存占用约为 FP16 的 1/4，推理快、精度略有损失。

  本实验使用两个 Qwen2-0.5B 模型对比：

  ┌───────────┬───────────────────────────────┬──────────┬────────────────┐
  │   引擎    │             模型              │ 权重大小 │      特点      │
  ├───────────┼───────────────────────────────┼──────────┼────────────────┤
  │ vllm-fp16 │ Qwen2-0.5B-Instruct           │ 0.93 GB  │ 高精度，慢     │
  ├───────────┼───────────────────────────────┼──────────┼────────────────┤
  │ vllm-int4 │ Qwen2-0.5B-Instruct-GPTQ-Int4 │ 0.43 GB  │ 低精度量化，快 │
  └───────────┴───────────────────────────────┴──────────┴────────────────┘

  (4) 规则控制器（参考 ModeSwitch-LLM）

  推理策略 Agent 采用手写规则控制器（参考 ModeSwitch-LLM 的设计思想：量化模型在多数场景质量够用且延迟更低，作为默认；FP16 仅用于高复杂度场景）选择推理精度：

  输入特征：prompt 长度、预期输出长度、GPU 显存占用、队列积压

  决策规则：
  1. 用户显式指定精度 → 遵从
  2. 显存压力高（>0.98）→ 降级 INT4
  3. 队列积压多（>50）→ 降级 INT4
  4. 高复杂度（>100字符）+ 长输出 → FP16 保质量
  5. 中等复杂度（>20字符）→ FP16
  6. 短任务 → INT4 低延迟

  每次决策附带 reason 理由，用于演示时展示调度依据。

  (5) 一致性校验（交叉复核）

  一致性校验 Agent 采用双模型交叉复核策略：

  原结果（strategy 用 FP16 生成）→ 用 INT4 复核
  原结果（strategy 用 INT4 生成）→ 用 FP16 复核

  计算两个结果的相似度（difflib.SequenceMatcher）：

  sim(a, b) = SequenceMatcher(None, a, b).ratio()

  validated = sim ≥ 0.25（相似度阈值）
  confidence = high（sim≥0.5）/ medium（0.25≤sim<0.5）/ low（sim<0.25）

  (6) 显存监控

  监控 Agent 周期性调用 nvidia-smi 采集 GPU 显存占用率，写入 Redis 供策略 Agent 做负载决策：

  nvidia-smi --query-gpu=index,memory.used,memory.total --format=csv,noheader
  → {'gpu0': 0.90}   # 占用率
  → Redis gpu:usage（5秒过期，避免读到陈旧数据）

  4. 总结

  本实验在 Docker 环境下成功构建了多智能体协作的推理调度系统，通过三个 Agent（用户接口、推理策略、一致性校验）的协同，实现了对 FP16/INT4 双精度推理引擎的自动调度。系统在 16
  个并发请求下，规则控制器实现了 100% 的 FP16/INT4 分流准确率。

  核心成果：

  1. 角色定义：构建三个自治 Agent（gateway/strategy/validator），各自独立容器运行，职责清晰分离。
  2. 通信框架：采用 Redis 消息队列实现 Agent 间解耦的任务传递与协同，支持任务队列、结果发布订阅、监控数据共享。
  3. 推理优化：部署 FP16 与 INT4 双精度引擎，规则控制器（参考 ModeSwitch-LLM）根据任务复杂度 + 显存负载自动选择精度，分流准确率 100%。
  4. 一致性校验：validator Agent 采用双模型交叉复核，用另一精度模型复核原结果，计算相似度并标记置信度，有效识别低置信结果。

  技术收获：
  - 理解多智能体系统的角色划分与协作机制
  - 掌握 Redis 消息队列实现异步任务传递
  - 实践 vLLM 双精度引擎部署（FP16 + GPTQ-INT4）
  - 学习规则控制器（Rule-based Controller）的调度算法设计
  - 掌握 nvidia-smi 显存监控与负载感知调度

  存在问题：

  1. 单卡吞吐量受限：两个引擎共用单张 6GB 显卡，且 strategy 单线程串行消费任务，吞吐量仅 0.24 req/s。真正的多卡环境下两引擎分卡部署可显著提升吞吐。
  2. 一致性校验通过率低（6/16）：0.5B 小模型回答质量不稳定，FP16 与 INT4 答案差异大（相似度常 < 0.25 阈值），导致较多任务校验未通过。这反向验证了校验机制的有效性，但降低了可用率。
  3. WSL2 环境限制：WSL2 内存仅 7.44GB，两个 vLLM 实例的 CPU swap space 与共享内存易超限，需特殊适配（--swap-space 1 + shm_size 2gb）。

  改进方向：

  1. 并行消费：strategy Agent 改为多协程并发消费队列，提升吞吐量。
  2. 多卡部署：FP16 与 INT4 引擎分卡部署（GPU 0 / GPU 1），消除显存竞争，真正实现并行推理。
  3. 模型升级：换用更大模型（如 Qwen2-7B），提升回答质量与校验通过率。
  4. 学习型路由器：引入 ModeSwitch-LLM 对比实验，评估学习型路由器 vs 规则控制器在单卡场景的性能差异。

  5.1 推理策略 Agent（来自 strategy/main.py）

  规则控制器：

  @dataclass
  class Decision:
      strategy: str
      reason: str

  def choose_strategy(prompt, gpu_usage, queue_depth, user_strategy, max_tokens) -> Decision:
      # 1. 用户显式指定 → 优先遵从
      if user_strategy in ("fp16", "int4"):
          return Decision(user_strategy, "用户显式指定精度")

      prompt_len = len(prompt)
      long_output = max_tokens > LONG_OUTPUT
      gpu0 = gpu_usage.get("gpu0", 0.0)
      mem_pressure = gpu0 > MEM_PRESSURE
      batch_pressure = queue_depth > BATCH_PRESSURE

      # 2. 资源紧张 → 降级 INT4
      if mem_pressure:
          return Decision("int4", f"显存压力高(gpu0={gpu0:.2f})，降级 INT4")
      if batch_pressure:
          return Decision("int4", f"队列积压 {queue_depth} 个任务，降级 INT4")

      # 3. 高复杂度 + 长输出 → FP16
      if prompt_len > PROMPT_HARD and long_output:
          return Decision("fp16", f"高复杂度(prompt={prompt_len})+长输出({max_tokens})，用 FP16 保质量")

      # 4. 中等复杂度 → FP16
      if prompt_len > PROMPT_MEDIUM:
          return Decision("fp16", f"中等复杂度(prompt={prompt_len})，用 FP16")

      # 5. 短任务 → INT4
      return Decision("int4", f"短任务(prompt={prompt_len})，用 INT4 低延迟")

  任务消费主循环：

  async def main():
      r = redis.from_url(f"redis://{REDIS_HOST}:{REDIS_PORT}", decode_responses=True)
      async with httpx.AsyncClient() as client:
          while True:
              _, task_raw = await r.brpop(PENDING_QUEUE, timeout=0)
              task = json.loads(task_raw)

              # 采集系统状态
              gpu_usage = json.loads(await r.get(GPU_USAGE_KEY) or "{}")
              queue_depth = await r.llen(PENDING_QUEUE)

              # 规则控制器决策
              decision = choose_strategy(task["prompt"], gpu_usage, queue_depth, ...)

              # 分发到对应引擎
              url = VLLM_FP16_URL if decision.strategy == "fp16" else VLLM_INT4_URL
              result = await call_vllm(client, url, model, task["prompt"], ...)

              task["result"] = result
              task["strategy_used"] = decision.strategy
              task["strategy_reason"] = decision.reason
              await r.lpush(VALIDATING_QUEUE, json.dumps(task, ensure_ascii=False))

  5.2 用户接口 Agent（来自 gateway/main.py）

  @app.post("/infer")
  async def infer(req: InferRequest):
      task_id = str(uuid.uuid4())
      task = {"task_id": task_id, "prompt": req.prompt.strip(),
              "strategy": req.strategy, "max_tokens": req.max_tokens, "status": "pending"}
      await r.lpush(PENDING_QUEUE, json.dumps(task, ensure_ascii=False))
      return {"task_id": task_id, "status": "dispatched"}

  @app.get("/infer/{task_id}/stream")
  async def stream_result(task_id: str):
      async def event_stream():
          cached = await r.get(RESULT_KEY.format(task_id=task_id))
          if cached is not None:
              yield f"data: {cached}\n\n"
              return
          pubsub = r.pubsub()
          await pubsub.subscribe(RESULT_PREFIX.format(task_id=task_id))
          async for msg in pubsub.listen():
              if msg["type"] == "message":
                  yield f"data: {msg['data']}\n\n"
                  if json.loads(msg["data"]).get("status") == "done":
                      break
      return StreamingResponse(event_stream(), media_type="text/event-stream")

  5.3 一致性校验 Agent（来自 validator/main.py）

  def similarity(a: str, b: str) -> float:
      return SequenceMatcher(None, a, b).ratio() if a and b else 0.0

  async def cross_validate(client, task):
      # 用「另一精度模型」复核原结果
      if task.get("strategy_used") == "fp16":
          url, model = VLLM_INT4_URL, VLLM_INT4_MODEL   # INT4 复核
      else:
          url, model = VLLM_FP16_URL, VLLM_FP16_MODEL   # FP16 复核

      cross_result = await call_vllm(client, url, model, task["prompt"])
      sim = similarity(task["result"], cross_result)
      validated = bool(task["result"]) and bool(cross_result) and sim >= 0.25

      task["similarity"] = round(sim, 3)
      task["validated"] = validated
      task["confidence"] = "high" if sim >= 0.5 else ("medium" if validated else "low")
      task["final_result"] = task["result"] if validated else "校验未通过，结果可信度低"
      task["status"] = "done"

      await r.publish(RESULT_CHANNEL.format(task_id=task["task_id"]), json.dumps(task))
      await r.set(RESULT_KEY.format(task_id=task["task_id"]), json.dumps(task), ex=3600)

  5.4 显存监控 Agent（来自 monitor/main.py）

  def collect_gpu_usage() -> dict:
      out = subprocess.check_output(
          ["nvidia-smi", "--query-gpu=index,memory.used,memory.total",
           "--format=csv,noheader,nounits"], timeout=5
      ).decode()
      usage = {}
      for line in out.strip().split("\n"):
          idx, used, total = [x.strip() for x in line.split(",")]
          if int(total) > 0:
              usage[f"gpu{idx}"] = round(int(used) / int(total), 3)
      return usage

  async def main():
      while True:
          usage = collect_gpu_usage()
          if usage:
              await r.set(GPU_USAGE_KEY, json.dumps(usage), ex=5)  # 5秒过期
          await asyncio.sleep(2)   # 2秒采集间隔
